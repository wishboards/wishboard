---\ntitle: 0007 Ai Integration\n---\n# ADR 0007: Decomposable & Optional AI Integration

- **Status:** Proposed
- **Date:** 2026-08
- **Context Date:** 2026-08

## Context

Wishboard targets two primary deployment environments:

1. **Disconnected local hardware**: e.g., Raspberry Pi 4 running single-node Docker at conventions.
2. **Serverless cloud deployments**: AWS Lambda + Turso/libSQL + API Gateway + CloudFront.

We want to explore incorporating AI capabilities in three key areas:

1. **Rule & Attribute Generation**: Assisting admins with authoring rules and event taxonomies (`profile.yaml`).
2. **Attribute Inference**: Inferring missing attributes or suggesting refined tags based on raw wish text submitted by users.
3. **Search & Authoring Augmentation**: Providing semantic search (vector embeddings) and real-time wish drafting assistance.

However, running synchronous LLM inference on a Raspberry Pi 4 will cause severe CPU starvation and unacceptably high latencies, while cloud API calls incur financial cost and latency concerns for serverless Lambda execution.

## Decision & Proposed Architecture

AI capabilities in Wishboard must be **fully optional, decomposable, and asynchronous**.

### 1. Abstract Provider Architecture

AI functions will be abstracted behind interface adapters:

- `InferenceProvider`: For text analysis, attribute extraction, and tag recommendations.
- `EmbeddingProvider`: For generating vector embeddings for semantic search.

Wishboard will support three implementations:

- `NoopProvider` (Default): Performs no AI processing; preserves standard exact/rule-based execution.
- `LocalProvider`: Leverages lightweight, quantized models (e.g. via ONNX runtime or Llama.cpp) optimized for edge deployment.
- `CloudProvider`: Connects to commercial LLM APIs (e.g., Gemini, OpenAI) using configured API keys.

### 2. Asynchronous AI Worker Pattern for Wish Tagging

To avoid blocking web request handlers or CPU-stalling local deployments:

1. **Immediate Persist**: When a user creates or updates a wish, the wish is saved immediately to the database and returned to the client without waiting for AI processing.
2. **Background Queue**: If an AI provider is active (`ENABLE_AI_FEATURES=true`), an async background worker queues the wish content for processing.
3. **Non-destructive Suggestions**: The worker generates _suggested_ attributes and improvements without mutating the original wish directly.

### 3. User Experience (UX) Flow for Suggestions

- **Suggestion Badge**: In the user dashboard / wish management view, wishes with pending AI suggestions display an indicator badge/symbol.
- **Review Modal**: Users can click the wish to view proposed attributes/improvements and explicitly choose to **Accept**, **Reject**, or **Modify** the suggestions before they are applied.

### 4. Semantic Search via Vector Embeddings

- For deployments with AI search enabled, Wishboard will utilize libSQL's native vector search features.
- Content embeddings generated by the `EmbeddingProvider` will be stored in a `wish_embeddings` table.
- Fallback to standard SQL `LIKE` pattern matching when vector search is disabled or unavailable.

## Consequences & Next Steps

- **Zero Footprint Default**: Single-node Raspberry Pi deployments without AI configured suffer zero performance overhead.
- **User Control**: Users retain total control over their wish attributes, preventing AI hallucination from corrupting matching logic.
- **Extensibility**: Third-party developers can plug in custom local or cloud LLM providers without altering core Wishboard code.
- **Tracking**: Tracked in GitHub issue [#332](https://github.com/wishboards/wishboard/issues/332) and documented in `BACKLOG.md`.
